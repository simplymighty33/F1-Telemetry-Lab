# v0.10.0 完成圈增量分析与驾驶段

UDP → 原始写入 → 基础整理 → 独立增量分析。后三者不是同一线程。分析失败只暂停派生结果，不改变 Raw 保存流程。

## 实现边界

- `IncrementalAnalysisStore` 按 Raw offset 的索引范围消费基础缓存，每批限制包数。保留最多 256 个待拼接帧；低频车辆状态、轮胎观察、最终圈速历史与进度使用显式 JSON 压缩保存，不使用 pickle。
- 检查点、玩家样本、圈速、重采样、驾驶事件和驾驶段映射在同一 SQLite 事务中提交。FULL 同步、WAL 和系统所有的文件锁，防止第二个写入者。失败回滚后重载上次状态。
- 只对新完成、源样本变化、圈速历史修订、赛道长度变化或 Flashback 影响的圈重新分析。收到 2 Hz 的相同历史不会因为接收时间改变重绘全历史。帧尚未拼接完时等待，避免提前把缺失尾段认作完整圈。
- Flashback 即时撤销受影响圈的图表/指标，回退最终历史，再按新的有效分支生成。分析的完整历史引擎保留，作为回归验收参考和 CSV 导出路径。
- 每个驾驶段以游戏的车库状态划分，不以胎组变化划分；比赛进站不必产生新段。段 ID 取起点 Raw offset，回溯后刷新有效范围。一个完成圈若跨段，显示归属最后包含其有效样本的段；图表仍保持完整圈，而不切掉该圈的早期样本。
- 图表显示距离域比较，不是教练建议；沿用现有 5 m、90% 距离覆盖门槛。质量表解释无效圈/不足样本/不足覆盖/等待。覆盖率不是 UDP 无丢包证明，也尚未包含最大时间间隙门槛。
- 正常后台处理通常有数秒帧拼接/历史延迟。关闭时停止 Raw 后等待基础整理，再等待分析；落后超过预算时保存检查点，离线恢复。强杀和断电可能损失最后未提交的部分，但不会主动修改 Raw。

## 使用与兼容

默认 `foundation_enabled=true`、`analysis_enabled=true`；自动分析也可单独关闭。分析窗口优先打开当前采集 Session，每 1.5 秒检查提交状态；保留当前圈和段选择，无效选择自动清除。历史数据库只读兼容，默认派生文件是独立 `analysis_v0.10.0/telemetry_analysis.db`。

命令行默认增量；`--export`、`--include-invalid`、`--force-rebuild` 明确走全量参考引擎，默认输出为独立 `analysis_v0.10.0_reference`。如果指定了已有增量数据库的目录，将拒绝覆盖。Raw 首次转换仍需要遍历源文件；优化针对以后新增数据与重复打开，不声称首次转换瞬时完成。

## 长测验收

对 624,609 包的 F1 23 长测记录分 10,000 包一批，并在每批后关闭/重开分析器。12 次 Flashback、11 个有效单圈、11,603 个距离点；12 个原有数据表（含轮胎）的全部行与完整重放基准一致，原 Raw SHA-256 不变。首次增量约 16 秒，已处理数据重新打开约 0.035 秒（本机单次测量，不代表所有硬件）。完整机器可读结果见 `outputs/incremental_v0.10.0_long_final/incremental_verification.json`。

还需玩家电脑进行真实长时间、资源占用与各游戏版本实测。构造协议包的通过不等同于所有游戏模式真实运行验收。

发布前 99 项自动化测试全部通过。每秒 1,000 个合成包的 25,000 包 UDP 验收中，接收、Raw、索引、基础缓存、增量分析数量全部相同，SQLite 完整性为 ok，无后台错误。测试进程内存约 30.5 MiB，峰值约 41.4 MiB；25.31 秒墙钟时间消耗 5.06 秒进程 CPU 时间（约单核 20%，不是整机 CPU 百分比），未运行游戏，不用于推断帧率影响。分发文件夹约 22.6 MiB，无新增第三方运行依赖。

最终打包程序通过 2023/2024/2025/2026 构造包接收、轮胎记录、后台分析、端口重载、独立分析窗口、主窗口与分析窗口安全关闭弹窗验收。报告位于 `outputs/release_v0.10.0_final/release_verification.json` 与 `outputs/stress_v0.10.0_final/stress.json`。真正的赛中体验仍建议跑几圈、回车库、撤回一圈再重跑，以及切换两个驾驶段核查。
