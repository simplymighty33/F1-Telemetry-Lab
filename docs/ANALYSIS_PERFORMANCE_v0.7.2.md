# 离线分析入口修复与性能研究

日期：2026-09-30。环境：Windows 10、Python 3.13.15、本机 18 个逻辑处理器。计时结果是本机测量，不是游戏电脑的性能保证。

## 已发布修复：v0.7.2

后台结果队列原本错误地放在 `ComparisonChart`，而后台任务和回调访问的是 `AnalysisWindow._build_results`。现已将队列移至实际使用它的窗口对象，修复“从 Session 生成分析”和“压缩旧 Raw”的结果、错误反馈与按钮恢复。窗口关闭后不再继续处理轮询结果。

30 项自动测试全部通过，覆盖后台线程成功/失败、真实 Raw 转换及原有采集与分析功能。另对完整长测执行真实 GUI 后台生成：624,609 包、0 解析错误、11 圈、11,603 个重采样点，自动载入后显示 1,055 个两圈共有距离点，两枚按钮均恢复为 normal。该界面流程约 36.18 秒。正常桌面环境下实际发布 EXE 已成功载入分析数据库，并在关闭窗口后以退出码 0 结束。

先前版本可能在后台生成完成后仍显示“正在分析”，因此用户观察到的持续等待不一定等于算法本身耗时。在原长测目录中现已有 `analysis/telemetry_analysis.db`，可以直接用“打开分析数据库”载入，无需再生成一次。

## 测量设计与结果

数据源：v0.4.0 的 `session_20260929_195937/raw_packets.bin`，670,711,502 字节、624,609 包。所有分析输出写入隔离目录，原 Raw 未修改。优化实验在独立进程中进行，不改写应用源码，不替换正式发布 EXE。

| 场景 | 总耗时 | CPU 时间 | 校验 |
|---|---:|---:|---|
| 当前构建逻辑，v1 Raw | 30.58 秒 | 30.55 秒 | 11 张数据表逐行一致 |
| 优化原型，v1 Raw | 13.65 秒 | 13.56 秒 | 11 张数据表逐行一致 |
| 优化原型，同一数据的 v2 Raw | 13.21 秒 | 13.13 秒 | 11 张数据表逐行一致 |
| 打开已有数据库并构建两圈对比，连续三次 | 0.013–0.017 秒 | 未单独测量 | 11 圈、1,055 对比点 |

原型在同一 v1 文件上的耗时减少约 55.4%，速度约 2.24 倍。v2 一项同时改变了输入格式，不能将其与 v1 的差异全部归因于解压或压缩。数据库读取计时不包含 Tk 窗口创建和绘制，也不是尚未实现的自动缓存功能计时。

当前构建逻辑的阶段耗时：

| 阶段 | 耗时 |
|---|---:|
| Raw Replay、解析、数据库写入及收尾 | 28.69 秒 |
| 距离重采样 | 0.92 秒 |
| 驾驶事件与指标 | 0.07 秒 |
| CSV/压缩 CSV 导出 | 0.91 秒 |

因此优先优化解析有明显收益。重采样不是这份数据的主要瓶颈。50,000 包的性能剖析记录了约 1,413 万次函数调用；逐字段 `_read_schema`、完整 Session History 解码、重复的 `schema_size` 计算，以及帧组装是主要开销。

一致性比较覆盖：sessions、events、laps、telemetry_samples、lap_analysis、resampled_lap_samples、braking_events、throttle_events、gear_shift_events、lap_metrics、session_metrics。按 rowid 遍历每行、序列化并比较 SHA-256；不比较创建时间和源路径等 metadata。最终仍为 11 圈、12 次 Flashback、0 解析错误，原始/被回溯分支的审计痕迹均保留。

## 可落地的优化顺序

### 1. 已生成结果的复用，解决重复等待

已有“打开分析数据库”入口本身很快。下一版本应在选择 Session 后，识别是否存在兼容分析，提供“打开已有结果”和“重新生成”；在可靠校验后可默认复用。

缓存键至少覆盖 Raw 标识/文件大小/高精度修改时间、分析引擎与 schema 版本、距离步长、无效圈选项、事件阈值。首次构建宜保存源文件内容指纹，并在构建结束验证源未变化。文件被追加、替换、算法或参数变化时须失效。严格校验需要读取源文件确认内容指纹，因此不能承诺完整指纹校验与 0.015 秒数据库读取同样快。正在录制的 Session 不能当成已完成的稳定缓存。

### 2. 预编译整条记录的二进制解析器

原型将固定 schema 合成为一份小端 Struct，一次展开整条记录，再按固定索引组装字段；编译结果和记录尺寸用有界缓存复用。避免每包、每字段反复创建 Struct 和计算尺寸。数组仍按原有顺序输出，字段类型不变，不增加第三方依赖。Python 官方说明复用 Struct 能避免重复编译格式；正式实现还需测试所有 packet schema、数组、名字字节串和异常长度。[Python 3.13 struct 文档](https://docs.python.org/3.13/library/struct.html#struct.Struct)、[有界缓存文档](https://docs.python.org/3.13/library/functools.html#functools.lru_cache)

### 3. 单圈分析只展开所需历史

原型对固定长度的 Session History 先读取车辆编号：AI 历史不进入玩家圈分析的 100 条历史展开；玩家历史包体未变化时复用已解析快照，但仍更新接收时间。Raw 仍逐包读取并验证 CRC，所有 AI 原始包都保留；不改变“完整包解析”工具的能力，也不丢弃 Flashback 事件。末次快照必须覆盖旧快照，不能只追加已完成圈。

### 4. 再评估写入批次与索引构建时机

若前三项后数据库成为主要瓶颈，再测量批量插入和延后建立部分索引。Flashback 之前必须写出待处理帧，否则 superseded 标记可能遗漏尚未落库的分支；不能只为速度调整事务却改变回溯结果。本次尚未改动事务或索引策略。

### 5. 进度和后台隔离

为 Replay、重采样、指标、导出分别显示进度和耗时；提供取消，并保证旧的完整分析库不被半成品替换。必要时将离线分析迁到独立进程，避免 Python 解码争用采集线程；这主要保障响应与实时采集隔离，不能直接承诺解析速度按核心数倍增。当前原型不启用实时全量分析。

## 交付边界与复现

v0.7.2 是入口修复版，尚未包含上述性能原型和自动缓存。原型属于本次研究材料；采用前应补充跨 Session、玩家编号改变、Flashback、坏包、截断 Raw、缓存失效和实际 EXE 构建测试。该材料证明优化方向有可测量收益，不代表跨电脑或跨游戏模式都能达到相同加速倍数。

- `work/benchmark_analysis.py`：阶段计时及 11 张表逐行校验。
- `work/analysis_fast_prototype.py`：隔离进程中的实验性加速。
- `work/verify_analysis_gui.py`：完整长测实际后台按钮流程，输出放在隔离目录。
- `outputs/analysis_performance_v0.7.2/`：基准、原型、GUI 验证 JSON。

原始长测 Raw、旧发布目录和原有分析结果均不被研究脚本替换。
